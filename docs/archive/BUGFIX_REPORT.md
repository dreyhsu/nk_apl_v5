## 結論先講

這份附件的**設計**是紮實的：連續命中(min_consecutive_hits) + 持續時間(hold_ms) +
逾時(timeout_sec) + Alarm Latch/Ack + strict_order 可切換 + OK ANY/ALL + NG 硬性拒絕 +

不需要重寫。

但你說「一大堆bug無法正常運作」是真的——我沒有只看它附的自我審查文件就相信它「已修好」，
而是實際把伺服器跑起來、灌測試資料、真正打 API 驗證，抓到一個**會讓整個離線影片SOP推論
功能100%當掉**的臨界bug。這剛好就是你最在意的那個功能：「不用相機，載入影片跑SOP」。

## 找到的問題

**位置**：`server.py`，`/api/video/sop_stream_infer`（離線影片 SOP 推論的 SSE 端點）

**現象**：不管上傳什麼影片、SOP 設定成什麼樣子，只要呼叫這支 API 就是 500 錯誤，一次都
沒有成功過。

**重現方式**（我實際執行過，不是猜測）：
1. 建立產品、上傳參考圖、存 region、建立一個 Step（帶一個 OK 樣板）、啟用 SOP config
2. 上傳一段測試影片、拿到 token
3. 打 `GET /api/video/sop_stream_infer?token=...&product_id=...&infer_fps=5`
4. 得到：`500 Internal Server Error`，伺服器 log 顯示：

```
UnboundLocalError: cannot access local variable 'start_time' where it is not associated with a value
  File "server.py", line 2729, in generate
    frame_index = int(round(start_time * fps))
```

**根本原因**：經典 Python 閉包陷阱。`start_time` 是外層函式 `video_sop_stream_infer()`
的區域變數，內層 `generate()` 在後面有一行 `start_time = frame_index / fps`——只要函式
內任何地方對某個名稱賦值，Python 就會把它視為整個函式的區域變數，於是前面「讀」
`start_time` 的那一行反而變成讀取一個「還沒被賦值的區域變數」，直接拋錯。

**諷刺的地方**：這是 v1.4 為了修「從影片中段開始推論時，SOP Timeout 誤把 seek 前的時間
算進去」這個問題時，順手引入的新 bug——修正意圖是對的，但寫法直接踩到閉包陷阱，導致
連 `start=0`（從頭播放）都一起壞掉，不是只有「從中段開始」這個原本要修的情境壞。它附的
`VIDEO_LABEL_AND_SYSTEM_REVIEW.md` 完全沒抓到這個，因為他們的測試腳本（`smoke_test.py`／
`flow_designer_test.py`／`live_flow_graph_test.py`）都沒有真正打過這支 SSE API 去跑一次
完整流程，只測到 Engine 邏輯本身跟 payload 格式，沒測到 HTTP 層真的能不能被呼叫成功。

## 我做的事

1. 用 `git diff` 等級的最小改動修正：把後段的 `start_time = frame_index / fps` 改成寫入

   語意跟原本想要的行為完全一樣（clamp 後的秒數仍然拿去算 `virtual_base`），只是不再共用
   變數名稱。

   全部掃過一遍，找「巢狀函式對外層變數重新賦值」這個特定 pattern，確認**這是唯一一處**，
   不是還有其他地方也埋著同樣的雷。
3. 修好之後，重新跑一次完全一樣的重現步驟：現在回傳 `200`，SSE 正確吐出每一幀的推論
   結果，最後 `done` 事件是 `"verdict": "COMPLETE", "pass": true`，功能正常運作。

## 第二輪稽核（針對原始需求做的額外驗證）

修好上面那個 bug 後，我又設計了幾組測試，針對性驗證跟你最初需求最相關的行為。過程中
抓到兩次自己測試資料的問題，一併記錄下來，避免誤判：

### 1. `strict_order: false` — 跨時間、不照順序累積（你最初的核心需求）

用一段「StepB 的畫面先出現、StepA 後出現」的影片測試：
- `strict_order: false`：兩個 Step 都正確完成，跟出現順序無關，最終 `COMPLETE`
- `strict_order: true`：正確擋下 StepB 提前完成，觸發「步驟遺漏：請先完成 [1] StepA」
  警報，StepA 之後補上仍是 `DONE`，但 StepB 的畫面已經過去、沒有重出現，最終正確判定
  `INCOMPLETE`

結論：這個系統本來就支援你要的「不用同時出現、不用照順序」模式，只要把
`strict_order` 設成 `false`，不需要我另外加邏輯。

*（過程中第一次測試我自己的參考圖跟影片畫面解析度沒對齊，導致畫面被拉伸變形、A 樣板
誤判失敗——這是我的測試資料問題，不是系統的 bug，修正測試方法後才拿到上面乾淨的結果。）*

### 2. NG 樣板硬性拒絕 + Alarm Latch + Ack

用「先出現 NG 異常畫面、再出現正確 OK 畫面」的影片測試，`alarm_latch: true`：
- NG 命中當下立即觸發警報、Step 不能算完成
- 之後 OK 畫面出現，Step 正確完成（DONE）
- 但警報仍保持 `active`，直到呼叫 `POST .../ack` 才清除 —— 這正是 README 講的
  「即使後續步驟都完成，仍須 Ack 才能 Gate PASS」，行為正確

*（這裡我也踩到一次自己的坑：我隨手畫的 NG 樣板圖案座標算錯，裁出來的模板其實是一整塊
純黑色。OpenCV 的 `matchTemplate` 對「整塊同一顏色」的模板做正規化相關係數比對時，數值
本來就不穩定，容易對任何同色色塊給出虛高分數，導致 NG 誤判命中一堆本來不該中的畫面。
這跟系統邏輯無關，是我準備的測試素材本身有瑕疵，修正樣板圖案後重測就正常了。這也是一個
對你們實際佈署有意義的提醒：樣板圖盡量避免大面積純色、低紋理的畫面，不然任何比對系統
都容易在這種畫面上出現不穩定分數。）*

### 3. 多路串流（VIDEO 來源）EOF / 非循環播放

用上面驗證過的乾淨素材，改用 `/api/stream-sources` 建立 VIDEO 型別來源（`loop_video:

這三項都符合 README 裡的既有承諾，沒有發現新問題。

## 第三輪：Video Label 資料模型重新設計（v1.5）

這輪不是找 bug，是你直接說「整個系統使用上就是很奇怪」之後，針對已經具體診斷出來的
Video Label 問題做的重新設計。範圍界定：只動 Video Label 的標註資料模型與存檔邏輯，
沒有動 multi-stream／monitor／offline-infer 這幾頁——那幾頁前兩輪已經個別驗證過是正常
運作的，沒有理由跟著重寫。

### 根本問題

`video-label` 存檔是「整批 region 從同一張畫面重新裁切」，不是「每個 region 記得自己
來自哪張畫面」。這代表如果你先在影片 A 的某一幀畫了框，之後換影片 B 又畫了框，兩批框
混在同一次存檔送出去，影片 A 那批會被靜默裁成影片 B 畫面上同樣座標的錯誤內容——沒有
報錯、沒有警告，你事後也無從得知。DB schema 裡也完全沒有欄位記錄「這個 region 來自哪支
影片、第幾幀」，一存檔這個資訊就永久消失。這就是你問「有紀錄label的偵嗎」背後的答案：
沒有，而且這個「沒有」本身就是問題根源。

### 修正內容

**後端（`server.py` / `save_regions`）**：改成逐筆決定裁切來源。每個 region 可以帶自己
的 `source_image_b64`；已存在的 region 如果這次沒帶，就完整保留原本內容，不再被別的
畫面覆蓋。新增 `POST /api/products/<pid>/regions/<rid>/attach-to-step`，可以把一個已存檔
的 region 直接掛成某個 Step 的 OK/NG 樣本，不用整批覆寫，也不用來回切換兩個頁面。

**前端（`video_label.html`）**：
- 每個新畫的框，畫下去那一刻就記住自己是從哪張畫面畫的，不再依賴存檔當下畫面是什麼
- 新增「📌 Pin to workspace」，選用功能——要同時處理好幾張畫面時才需要按；不按的話整個
  操作流程跟以前一模一樣，沒有多餘步驟
- 已存檔的 region 那一列新增「+ Step」按鈕，直接指派到某個 Step（不存在就順手建立），
  取代原本「存檔→切到SOP設計頁→翻找剛存的region→掛上去」那一長串

### 驗證

- 用實際 API 呼叫重現過修正前會出事的情境（同一次存檔混舊region+新region）：舊 region
  存檔前後樣板內容逐位元組比對完全相同；新 region 正確對應自己的畫面，兩者互不污染
- 模擬完整新版操作流程（釘選兩張畫面分別畫框→混合存檔→分別指派到不同Step）：全程正確
- 原有三個測試腳本（`smoke_test.py`／`flow_designer_test.py`／`live_flow_graph_test.py`）
  維持全部 PASS
- 離線影片 SOP 推論（前兩輪修好的功能）重新跑一次，確認沒有被這輪改動波及，正常
  `COMPLETE`

## 第五輪：v1.6.1 — 三個實際使用後回報的問題

這輪不是我自己找的，是你實際用過 v1.6 之後回報的三個具體問題。逐一列成因、修正、驗證。

### 問題1：影片有時候載入是顛倒的

**根因（已用實際影片證實，不是猜測）**：手機錄影常帶「旋轉 metadata」，`cv2.VideoCapture`
有沒有自動套用這個旋轉，**取決於安裝的 OpenCV／FFmpeg 組合**，`requirements.txt` 只釘了
`opencv-python-headless>=4.8`（下限，不是精確版本），不同機器裝到的版本行為不一致——這就是
「有時候」的來源。程式碼裡原本完全沒有明確處理旋轉，整個依賴這個不保證一致的隱性行為。

**驗證方式**：用你提供的實際測試影片（帶 180° 旋轉標籤），先用 `CAP_PROP_ORIENTATION_AUTO`
關閉自動旋轉，證實原始讀取確實是顛倒的（有圖為證）；再套用新寫的偵測＋校正邏輯，證實不管
自動旋轉這個隱性行為存不存在，都能正確轉正。

**修正**：新增 `get_video_rotate_code()` / `apply_rotate_code()` / `rotated_frame_size()`
共用函式（`vision_core.py`），明確讀取旋轉角度、自己套用，不再依賴環境隱性行為。套用到全部
9 個讀取影片幀的地方：`/api/video/upload`、`/api/video/frame`（Flow Studio 標註頁用的）、
`/api/video/infer`、舊版 `/api/video/stream_infer`、主要的 `/api/video/sop_stream_infer`、
多路串流的 `StreamWorker`、以及獨立生產伺服器用的 `infer_loop_opencv`。三條主要路徑
（標註頁擷幀、離線SOP推論、多路串流）都用你的實際影片重新跑過一次，畫面確認正確轉正。

### 問題2：不同 frame 的 label 框看起來都一樣

**根因**：`drawOverlay()` 疊圖時是把 `VL.regions` 全部畫出來，沒有依照「目前顯示的是哪一張
畫面」過濾——每個框本身有記住自己屬於哪一張畫面（`_captureId`，這是 v1.5 就有的機制，用於
存檔安全），但「顯示」那一半沒有跟著判斷，導致切換畫面時看到的是所有畫面的框疊在一起。

**修正**：`drawOverlay()` 只畫「屬於目前啟用畫面」的框。同時發現一個更根本的邊界情況並一併
修掉：如果使用者完全沒按過「釘選到工作區」就直接畫框（最常見的簡單用法），框的 `_captureId`
會是 `null`；一旦之後又按了 Pin，`null` 這個值的意義就會變得模糊。改成畫框當下如果還沒有
啟用中的釘選，會靜默自動建立一個，讓每個框永遠對應到一個真實存在的畫面記錄，不再有
語意會隨時間改變的 `null`。

**驗證**：用 jsdom 實際執行，模擬「先不點Pin直接畫框→再點Pin切到另一張畫面畫框→在兩張
畫面間切換」，確認每次切換畫面後，`drawOverlay` 只會畫出當下這張畫面自己的框，不會混到
別張畫面的框。這個測試在第一版修正時就抓到上述的 `null` 邊界問題，修正後重測通過。

### 問題3：沒有地方看到 label 縮圖或影片的哪一秒

**根因**：兩個獨立的缺口——時間點記錄的是「按下當下的電腦系統時間」
（`new Date().toLocaleTimeString()`），根本沒有記影片播放到第幾秒；縮圖則是完全沒做，
只存了完整畫面、沒有裁出小圖顯示。

**修正**：新增 `currentVideoTimeLabel()`，記錄影片自己的播放秒數（格式如 `0:23`），畫框
與釘選畫面時都改用這個。新增 `makeThumb()` 非同步裁出縮圖，畫框後自動觸發，完成後表格會
自動補上縮圖（裁切前顯示暫時的佔位符，不會卡住其他操作）。表格新增「縮圖」欄，Label欄下方
補上時間點；工作區縮圖列也把時間點從 hover 提示改成直接顯示在圖上。

**驗證**：用 jsdom 實際執行整段流程，確認時間點正確對應到設定的影片秒數（不是系統時間）、
縮圖確實非同步產生並在表格重繪時出現、表格列數與內容都正確。

### 這輪沒有做到的部分

90°／270° 旋轉的方向（順時針或逆時針）是照 OpenCV 官方慣例實作的，只用手上這支帶 180°
標籤的影片驗證過（180°本身順逆時針結果相同，不能驗證方向對不對）。如果你們現場有 90°
或 270° 旋轉的影片測出來還是不對，麻煩告訴我，我用那支影片重新校正方向。

## 第七輪：v1.6.3 — 縮圖仍是空的、標籤仍然疊在一起

第二張截圖顯示同一個問題還在，而且多了一個新資訊：Thumb 欄位完全是空的。仔細比對後，
這次是兩個更根本的原因，v1.6.2 那輪只在「當次操作」的情境下測過，沒有測「存檔後重新整理
頁面、重新載入這個產品」這個情境——這正是截圖裡發生的狀況。

### 縮圖是空的：根因

縮圖產生的程式碼只掛在「畫框那一刻」（`drawEnd`）。截圖裡的 6 個 region 是**上一次操作
已經存檔、這次重新選這個產品時從伺服器讀回來的**，從來沒有經過 `drawEnd`，自然沒有縮圖。
而且拿既有 region 列表的 API（`/api/products/<pid>/regions`）本來就刻意不回傳裁切好的
圖片內容（保持編輯器列表輕量），前端也沒有另外去要圖片。

**修正**：新增 `GET /api/products/<pid>/regions/thumbs` 端點，一次回傳一個產品所有
region 已經存檔的樣板小圖（不是重新裁切、是直接拿當初存檔時裁好的那張，保證跟實際比對
用的圖一模一樣）。`fetchRegions()` 載入既有 region 列表後，會再打這支端點把縮圖補上。

### 框還是疊在一起：根因（這個比較根本，要老實講清楚）

v1.6.1／v1.6.2 那兩輪修的 `_captureId` 過濾機制，是**瀏覽器記憶體裡、這次操作階段才有的
資訊**，從來沒有存進資料庫。存檔到資料庫的只有裁切好的小圖本身（`template_b64`），沒有
「這個 region 原本是從哪一張完整畫面框出來的」這個資訊。所以只要存檔後重新整理頁面、或
重新選一次這個產品，所有 region 的 `_captureId` 都會變成「沒有歸屬」，在沒有任何畫面被
釘選的狀態下，過濾邏輯的結果就是「全部一起顯示」——這跟 v1.6.1 修的其實是同一段邏輯，
但那一輪的測試只測了「同一次操作內」的情境，沒有測「重新載入」，所以沒抓到這個。

**這裡有一個要跟你講清楚的架構限制**：目前資料庫的 `regions` 表格本來就只有一個
`reference_img_b64`（存在 `products` 表格），不是每個 region 各自記自己的來源畫面。這是
系統從最早（還沒有「釘選多張畫面」這個功能之前）就有的設計——當時的用法就是「一個產品、
一張參考圖、圖上框多個 region」，全部疊在同一張圖上顯示本來就是對的。「跨多張畫面標註」
是後來加的功能，只解決了「這次操作不要搞混」，沒有解決「存檔後還記得住」，因為要記得住
需要資料庫多存一個欄位（每個 region 對應到哪一張畫面/哪一組），這是目前沒有的。

**這輪確實修正、且已驗證的部分**：
1. 縮圖補上了（不管是不是同一張畫面來的，都會顯示正確的小圖，因為是直接讀存檔內容，
   不是靠猜）
2. 畫面上多個框重疊時，標籤文字不再全部疊在同一個角落看不清——沒被選取的框只顯示精簡
   編號徽章，選取中的框才顯示完整文字，而且加了簡單的碰撞閃避，重疊的標籤會自動往下錯開

**這輪沒有修、需要你決定要不要做的部分**：如果這 6 個 region 原本確實是從不同畫面框的
（不是同一張照片上的 6 個不同區域），重新整理頁面後它們還是會顯示在同一張參考圖上——
這是前面說的資料庫欄位限制，要解決需要新增一個欄位存「這個 region 屬於哪一組畫面」，
存檔／讀取／顯示三處都要跟著改，是比這幾輪都大一點的改動。麻煩你確認一下：這 6 個
region 實際上是同一張照片上框的（那現在疊在一起顯示其實是對的、只是之前標籤看不清），
還是真的來自不同畫面（那就需要做這個比較大的架構調整）？確認後我再動工。

驗證方式：後端直接打新的 `/regions/thumbs` 端點確認縮圖內容正確；jsdom 重現「存檔後重新
載入」的情境，確認縮圖正確補上；用截圖裡實際的座標數字重現 6 個重疊 region，確認標籤碰撞
閃避邏輯正確運作、選取的框顯示完整文字、其餘顯示精簡編號。

確認過這 6 個 region 確實來自不同畫面/時刻，所以做了上一輪報告裡提到的比較大的架構調整。

### 新增的資料庫結構

新增 `capture_groups` 表格（`id, product_id, label, thumb_b64, created_at`），`regions`

### API 變更

- `GET /api/products/<pid>/regions`：多回傳 `capture_group_id`
- 新增 `GET /api/products/<pid>/capture-groups`：列出這個產品所有分組（含縮圖、region數量）

`saveRegions()` 存檔時，會幫這次工作階段中新建立、還沒存過的 Pin 分組（用縮小過的整張
畫面當縮圖，避免存進資料庫的東西太肥大）建立對應的 `new_capture_groups`，每個 region
依照自己的 `_captureId` 格式判斷要送 `capture_group_id` 還是 `capture_group_temp_key`。

### 驗證

後端：直接打 API 模擬「畫面A畫2個框、畫面B畫1個框、分兩次存檔」，確認兩組正確分開、
既有 region 沒被觸碰時正確保留原本分組。前端：jsdom 執行 `saveRegions()`，確認送出的
payload 正確包含 `capture_group_temp_key` 跟 `new_capture_groups`。**端到端**：完整模擬

不會再變成前兩輪那樣全部疊在一起。另外確認了 `flow_studio.html` 既有的存檔流程（完全
不帶 capture_group 相關欄位）在這次後端改動後仍正常運作，沒有破壞向下相容。

### 老實說清楚的限制

**分組縮圖是縮小過的版本（上限約480px），不是原始解析度。** 如果你之後選一個既有分組
繼續在上面加框，畫的框是基於這張縮小過的圖，精確度會比重新擷取一張全新畫面低一些。如果
需要高精度標註，建議對那個畫面重新擷取一次，而不是完全依賴分組縮圖。這是刻意的取捨——
如果每個分組都存原始解析度，資料庫會隨著分組數量快速肥大，跟原本「/regions 列表刻意不

region 顯示在擷取畫面的畫布/表格裡（畫框後直接指派給 Step，變成 Step 的樣板，不會留在
畫面上讓你瀏覽），所以不會遇到這一輪的問題，也就沒有套用這個修正——如果之後 Flow Studio
那邊也需要類似的「瀏覽這個Step過去用了哪些畫面」功能，是另外一個要討論的需求，目前沒做。

## 第十輪：v1.6.6 — 存檔後框的位置整個跑掉

### 根因

v1.6.4 幫分組畫面存縮圖時，我自己做了一個「聰明」的優化：把畫面縮小到最多 480px 再存，
理由是怕分組一多，資料庫存的原始解析度畫面太肥大。這個優化本身沒錯，但漏想了一件事：
**每個 region 的 x/y/w/h 座標，存的是「原始解析度畫面」上的像素位置**（例如 960×540 的
畫面上，座標可能是 352, 68, 269, 445）。畫布顯示畫面時，是拿「目前顯示的這張圖」的寬高
去算縮放比例（`S.scale = 顯示區域寬 / 圖片寬`）。如果重新載入時顯示的是縮小過的分組縮圖
（例如變成 480×270），畫布拿這張**縮小過的圖**去算縮放比例，但框的座標是對應**原始
960×540 畫面**算的——兩邊的「原始尺寸」認知不一致，框的位置跟大小就整個跑掉，這正是你
看到的「歪掉」。

我在 v1.6.4 交付時有提到「分組縮圖是縮小過的版本，繼續在上面加框精確度會比較低」，但
那時候只想到「精確度」的問題，沒意識到這個縮小其實會讓**既有的框整個顯示錯位**，這比
我原本講的影響嚴重得多，是我判斷失誤。

### 修正

分組畫面不再縮小，直接存完整解析度的擷取畫面——這樣「畫布顯示的圖」跟「框座標對應的
原始畫面」永遠是同一個尺寸，比例換算就不會錯。工作區縮圖列上那些 56×56 的小圖示不受
影響，本來就是瀏覽器用 CSS 把完整畫面壓縮顯示成小圖，不需要底層資料本身就是小圖。
拿掉了 `makeFullThumb()` 這個縮小用的函式，避免以後不小心又用到它重蹈覆轍。

### 驗證

兩層驗證：後端直接檢查存進資料庫的分組縮圖，實際解碼確認解析度真的是完整的 960×540，
沒有被縮小；前端用 jsdom 執行存檔流程，確認送出的 payload 裡分組畫面內容跟原始擷取畫面
逐位元組相同（沒有經過任何縮圖處理函式）。另外重跑第六到第九輪全部驗證過的情境，確認
這次修正沒有連帶影響其他功能。

## 第十一輪：v1.6.7 — 點表格列/縮圖，畫面沒反應

### 根因

跟前一輪的座標bug是不同問題。表格每一列的點擊事件，原本只會把這個 region 標記成「選取
狀態」然後重畫——但**不會判斷這個 region 屬於哪一張工作區畫面，也不會切換畫布去顯示那
張畫面**。如果你點的 region 剛好屬於「目前畫布顯示的這張畫面」，可以正常看到選取效果；
但只要點的是屬於**別張畫面**的 region（例如目前畫布顯示 Frame#1，你點了屬於 Frame#2 的
Region-2 那一列），`drawOverlay()` 的過濾邏輯會正確地把它排除在外（這部分沒有錯——它
本來就不屬於目前顯示的畫面），但因為畫布沒有跟著切換過去，你會覺得「點了完全沒反應」，
因為那個框確實存在，只是在另一張你目前沒在看的畫面上。

### 修正

點擊表格列（包含點縮圖，因為縮圖本身沒有另外攔截點擊事件，點擊會往上冒泡到整列的
點擊事件）時，先判斷這個 region 是否屬於目前顯示中的畫面：不是的話，先切換畫布到它
真正所屬的那張工作區畫面（呼叫既有的 `selectCapture()`），再標記選取、重新畫框——這樣
點下去一定會跳到看得到那個框的畫面，而且該框會用醒目的橘色標示出來。沒有分組資訊的
舊資料（`_captureId` 是 null）則退回顯示產品本身的參考圖。

# APL 1109｜Capture 期間持續取像與直播的修改計畫

實作更新（2026-11-09）：第一至三批的本機程式修改及第四批 ROI 調整已完成；PC 回歸通過。具體行為、測試及板端待驗收事項見[實作紀錄](../APL_CAPTURE_STREAM_ISOLATION_IMPLEMENTATION_20261109_ZH.md)。以下保留原設計與驗收標準，不代表 SmartCam 已完成驗收。

2026-11-09。目標版本為 APL_1109 的 `main@199972c`。本文是實作與驗收設計。比較基準為 10/15 的 `feature/apl-production-stream-optimization@1703439`。相關設定與既有測試基準見[版本盤點](../APL_1109_VERSION_REVIEW_20261109_ZH.md)。

**目標是讓檢驗可以慢一點，取像仍能前進。** 按下 Capture 時固定一張新鮮影像，判定、證據與 SN 都對應該張。檢驗期間，板端持續送出 H.264/RTP，外部 PC 持續解碼，操作員可看到工件正在檢驗。第一輪在同一套瀏覽器顯示條件下比較修改前後，才能知道後端改善了多少。

## 1. 已找到的等待點

| 路徑 | 1109 實際行為 | 設計上的影響 |
|---|---|---|
| QTI 相機 → 直播 | GStreamer 已用 tee 和獨立 queue 分成 JPEG 取像與疊圖編碼，後者經 H.264 → RTP → MediaMTX。見 [edge_runtime.py](../../edge_runtime.py) 的 QTI pipeline 建立處 | 沿用一個相機與編碼器。先改善 Python 工作排程。實際 RTP 是否停送要在板上量 |
| 手動 Capture → 預覽 | [apl_station.py](../../apl_station.py) 的 `inspect_snapshot()` 持有 `frame_lock` 做匹配，再持有站點鎖繪圖、存證與寫資料庫；相機迴圈的 `process_frame()` 也要取得這些鎖 | 操作員按下 Capture 後，預覽可能連下一張都處理不了 |
| 自動比對 → 下一張 | `EdgeRuntime._run()` 直接呼叫 `_auto_capture_tick()` → `evaluate_snapshot()`。命中後的提交才移到背景，提交時又對同一張做一次正式匹配 | 每次探測都可能拖延下一輪取像，命中時有額外的計算尖峰 |
| 狀態 → 資料庫 | 有活動工件時，`APLStation._snapshot_single()` 會執行 `SELECT COUNT(*) FROM attempts`。一輪預覽可以先由 `process_frame()` 取快照，再由 `station.status()` 取一次 | 即使移走 matcher，仍可能在預覽路徑等待站點鎖與 SQLite |
| 拍照 → 影格身分 | `capture_and_inspect()` 先讀時間，再在另一段鎖裡取照片，最後另讀 `frame_seq`。取像可能剛好在中間發布下一張 | 手動證據中的序號或新鮮度檢查有機會對到相鄰影格。這是原碼可見的競態，尚未觀察到產線錯配 |
| 顯示 → 疊字與瀏覽器 | [overlay_renderer.py](../../overlay_renderer.py) 會在狀態超過 3 秒沒更新時採用過期顯示；[apl_ui.js](../../static/apl_ui.js) 會依 API、影格序號與解碼新鮮度顯示或隱藏影片 | 只消失 ROI／疊字、整個預覽變黑、H.264 真正停送，三種現象可用不同訊號分辨 |

前次 PC 控制實驗分別暫停匹配與存證，並從第二條執行緒呼叫真正的 `process_frame()`。1109 在兩種情形下都等了 500 ms 仍未返回。10/15 版在匹配期間可返回，存證期間仍被擋住。500 ms 是實驗施加的延遲；SmartCam 的實際計算與 I/O 時間要另測。這也是不整批套用舊分支的理由。

## 2. 修改後的資料流

```text
相機 worker
  ├─ 疊圖 → H.264 → RTP → MediaMTX → WebRTC → 接收端 PC
  └─ JPEG → APL 取像 → 發布最新影格、序號、時間與相機世代
                         ├─ 預覽直接讀最近一次發布的站點狀態
                         ├─ 手動 Capture 固定指定影格 → 正式檢驗
                         └─ 自動檢驗只取最新候選 → 命中或逾時 → 正式提交
                                                            ↓
                                     同一張的原圖、結果圖、JSON 與 DB 紀錄
                                                            ↓
                                          發布正式結果 → 符合條件才允許 Step4
```

兩種工作有不同的取圖規則。**手動已受理的照片不可被新畫面取代；尚未開始自動比對的候選畫面可以被更新的一張取代。** 指標也要分清楚，設定檔的相機 30 FPS、APL 取像目標 10 FPS、自動探測上限 5 FPS，代表三個不同位置。

## 3. 建議分四批實作

### 第一批｜建立對照，讓取像與預覽避開檢驗鎖

主要改 [edge_runtime.py](../../edge_runtime.py)、[apl_station.py](../../apl_station.py)、[tests/test_snapshot_inspection.py](../../tests/test_snapshot_inspection.py)。

1. 先把上述 500 ms 實驗轉成可重複的測試。用事件控制 matcher、檔案準備、DB 提交三個停點，要求放行之前已能處理多張新影格。另測完整 runtime 的 `frame_seq` 持續前進，避免只測單一函式就判定已修好。
2. runtime 一旦取得有效新畫面，即以同一把短鎖發布影像參照、序號、單調時間與相機世代。採用發布後唯讀的影像，任何會畫框的路徑使用自己的副本。手動 Capture 在同一臨界區取這組資訊，沿用 3 秒新鮮度要求；新工作不讀上一輪開機或上一台相機的殘留照片。
3. 給 snapshot 模式獨立的預覽讀取路徑。預覽、硬體疊圖與 PATLITE 消費已發布的狀態；同一輪共享一份，忙碌時仍可取下一張。建立 matcher 移到站點初始化或受控的單次準備階段，明確回報尚未就緒。操作權限、工件、Step4 一律再檢查權威站點狀態；快照只供顯示。過期的分數與框要帶時間／世代，工件切換要清掉。
4. 拆開預覽與正式證據的發布。若先發布 raw，必須核對現有 `wait_jpeg(mode)` 同時支援 raw/result 的喚醒語意，避免把前一張 result JPEG 標成這一張；必要時使用各自的發布序號。JPEG 編碼與繪圖在鎖外進行，鎖內只交換完成的資料。
5. 活動工件的 `attempt_count` 在建立／恢復時從 SQLite 載入，成功提交後更新，換工件清零。或由同一份已提交狀態提供預覽需要的欄位。用測試檢查每張預覽的呼叫鏈已無資料庫查詢，也沒有另一個阻塞的 `station.status()`。

**交付條件**：即使手動檢驗或 DB 被測試刻意停住，取像序號仍增加；原圖中的辨識標記、證據序號與按鈕受理時的影格相符。這一批即能獨立比較按下 Capture 時的行為。

### 第二批｜縮短存證持鎖時間，完整提交後才可上報

主要改 [apl_station.py](../../apl_station.py)、[inspection_store.py](../../inspection_store.py)，沿用原本的證據目錄、歷史查詢、HTTP 回應與 SFIS request ID。

1. **受理**。在站點鎖內驗證工件與狀態，保留本次 attempt 身分、進入 `JUDGING`。以 cycle、站點世代、相機世代、attempt 和來源影格識別此工作。手動請求可沿用原本等待結果的 HTTP API；只有該請求等待，取像不等待。兩個操作員同時按下、或手動與自動同時進入，最多只受理一次正式提交。
2. **準備**。在鎖外匹配、繪圖、編碼兩張 JPEG、寫入此 attempt 專屬的檔案。JPEG/JSON 採相同檔案系統的暫存與原子替換。正式結果圖可用這次判定的局部資料產生；檔案就緒前，外部看到的工件仍為 `JUDGING`。
3. **提交**。提交前重驗工作身分與取消狀態。檔案已完成後，把 attempt、工件及對應事件放進同一個 SQLite transaction。現有 `save_attempt()` 與 `_write_save()` 各自有 `with self.db`，實作時需提供由同一交易管理的寫入入口。保留現有 WAL、同步耐久性以及同一連線的序列化。預覽讀獨立快照，即使 DB commit 慢也不等待這把鎖。
4. **發布**。DB 成功才發布 PASS／NOT_MATCHED、更新次數與允許 Step4。維持現行回應欄位及瀏覽器觸發 Step4 的方式。JPEG／DB 失敗要顯示可追查的存證錯誤，阻止上報，保留既有 recovery 行為。
5. **中途停止或斷電**。檔案與 SQLite 分屬兩種儲存，需覆蓋「檔案已完成但 DB 未提交」的窗口。以 attempt ID 辨認本次孤立檔案；重啟核對檔案與紀錄，只處理明確屬於未提交工作的檔案。用既有資料庫副本驗證舊紀錄可讀。對於提交結果不明的情形先依 ID 查核，避免重複建立或刪除已引用證據。

**交付條件**：延遲、磁碟滿、DB 提交失敗、提交前停止、成功提交後回應遺失都要有可辨認的結果。歷史中的每一筆成功 attempt 有同一張原圖、結果圖與 JSON。任何失敗或過期工作都不能觸發 Step4。

### 第三批｜自動比對在單一背景工作執行，保留產線時間規則

主要改 [edge_runtime.py](../../edge_runtime.py) 的 `_auto_capture_tick()`、`_start_auto_commit()` 與停止流程。可借用 10/15 版的過期工作檢查，按 1109 的規則整合。

- **負載上限**。最多一個正在運算的匹配工作；自動候選最多保留最新一張。手動 Capture 可先保留點擊那張，排在下一個可用時機，優先於尚未開始的自動探測。遇到進行中的正式檢驗，重複按鈕沿用忙碌回應。每張候選有唯一序號，跳過的時間槽不補跑。用同步原語管理工作所有權，不讓 reader、HTTP、probe、commit 同時修改同一組字典。
- **20 秒與兩次命中**。從 MCIO／Step1 就緒並實際開始自動檢驗時計時。建議採用單調時鐘，以截止前完成判定的兩個不同採樣影格才計入連續命中；中間實際判為未命中就歸零。明確測試剛好到期與遲到結果。現碼先看 hits、再看比對前計算的 elapsed；這項邊界規則是擬議修正，需和既有正式樣本一起回歸。
- **逾時處置**。正式設定 `5 FPS / 2 hits / 20 秒 / not_matched`。到期只登記一次；禁止遲到的一次命中經正式重算變成 PASS。保留原始匹配分數，另記時間規則的判定原因。逾時後可手動重拍並重新開始窗口。若連一張有效新圖都沒有，回報取像異常，不造一張證據或冒充視覺 NG。其他模式已有的 `timeout_action=pass` 單獨做相容測試。
- **結果與影格綁定**。相機、工件、attempt、matcher 設定任一項改變，放棄該工作的遲到結果。已受理的正式檢驗與確認投遞有唯一擁有者。當輸入像素、matcher 設定與規則完全一致，可重用該張的探測結果，消掉命中後對同一張重算的耗時；另以基準影像比對正式輸出的每個欄位。
- **關閉與重開**。Stop 先停止接新工作並使舊工作的發布資格失效，照現有路徑要求 QTI worker 停止並完成 EOS／NULL。背景工作的有界等待共用現行關閉期限；活著的 writer 仍握有 DB 時，禁止提前關閉其資源或重用為下一個工件。將新工作納入 [visionedge_server.py](../../visionedge_server.py) 的 shutdown 檢查，分開記錄硬體釋放結果與檢驗收尾結果。重新開機／相機重開後，舊工作結束也不能清掉新工作的狀態。

**交付條件**：故意讓單次比對超過 200 ms，實際 probe FPS 允許下降，取像持續前進。測試 20 秒邊界、手動優先、多個瀏覽器、Stop/Start、SFIS 慢回應與相機故障。每一輪的證據、PATLITE 狀態與 SFIS 工件身分一致。

### 第四批｜只做有量測依據的 CPU／串流優化

| 優先順序 | 改動與驗證 |
|---|---|
| 先做 ROI 對照 | [apl_matching.py](../../apl_matching.py) 現在先將全張 1920×1080 轉灰階。評估沿用 10/15 的做法，先裁 431×588 搜尋區再轉灰階。保留全圖座標、7 類 20 張模板、閾值與反例分差。比較 PC 與板端每張耗時，核對 PASS/NG、框、最佳模板與分數，含接近門檻的影像 |
| 若 CPU 仍高 | 量測 worker JPEG → parent 解碼 → raw/result JPEG 編碼、重複畫框、Cairo 疊圖各自成本。先消除同一輸入與輸出設定上的重複工作；若要重用 JPEG 必須核對 JPEG 品質、旋轉、座標、raw/result 與錄影需求。以取像、檢驗及 WebRTC 三方數據決定效益 |
| 若板上仍有 RTP 缺口 | 在編碼器前、`h264_tee` 後及送到 loopback 的 RTP 分別取時間與數量。現有 `stream_queue` 可丟舊的 H.264 buffer；過載時有機會缺少解碼所需的參考畫格。先定位 queue overrun、上游停產或網路遺失，再決定原始影格的丟棄位置、關鍵影格恢復或編碼器處理。直接改成阻塞 queue 可能反向拖住共享錄影分支 |
| 若只有頁面黑屏 | 當同一段時間 RTP 持續、接收端解碼仍前進，另案修正 UI 對 API／`frame_seq` 的依賴。若只有 ROI／字消失，查疊字狀態的更新年齡與工件世代。兩種情況均可由同一組記錄定位 |

## 4. PC 與 SmartCam 如何驗收

**量測方式**。兩版使用同一台開發 SmartCam、同一接收 PC、網路、畫面、模板與設定。先記錄實際啟動路徑、版本、服務使用的 YAML，以及 UI 視圖確為 WebRTC Result。診斷用單調時間計算間隔，用 UTC 與測試輪次對齊板端和 PC。每輪記錄 Capture 受理、取圖序號、比對、JPEG 準備、DB 提交、正式結果；用週期摘要記錄實際 probe FPS、被取代的候選數、取像最大間隔。避免逐封包寫板上日誌。

| 情境 | 執行與通過條件 |
|---|---|
| PC 阻塞與正確性 | 各別卡住匹配、準備檔案、DB 提交；放行前確認多張新影格已發布。以內容帶序號的影像比對送入 matcher 與存入證據的原圖。併跑兩個 Capture、自動命中與手動申請，對照 DB/event 數量。用暫存 DB 與替身 SFIS |
| PC 異常／相容 | 覆蓋磁碟滿、提交失敗、恢復舊 DB、上報重試沿用 request ID、各階段 Stop、慢工作跨世代、逾時、無新影格。另跑瀏覽器影片模式、檔案回放、舊多步模式、PATLITE、錄影與相機關閉回歸。記錄版本盤點已有的 2 項失敗、4 項跳過，逐項比對新增退化 |
| 板上正常與慢檢驗 | 建議每版先做 60 秒待機基線，再各做 10 輪手動 Capture、10 輪自動命中、3 輪 20 秒逾時。開發板用測試工件與隔離的 SFIS 測試端；另選至少一輪在測試工具中注入 6 秒慢匹配、慢存檔，跨過原本 UI 的 5 秒界線。生產設定不寫入故障注入開關 |
| 接收端與實際出流 | 同步採樣 APL `frame_seq`、SmartCam loopback `udp dst port 5004` 的 RTP 序號及時間戳、MediaMTX 的 `smartcam` 路徑／session 記錄，以及接收 PC 同一 peer 的 `bytesReceived / framesDecoded / keyFramesDecoded`。另記是否為黑屏／疊字消失、API 延遲與是否新建 session。封包數和 `service active` 各自只能證明其中一段 |
| 壓力與生命週期 | 留一輪兩個接收端、一輪有錄影、一輪依正式班次做長時間運行。慢檢驗中停止並重開相機至少 4 輪，每次取得新影格與正確工件狀態，停止有可核對的 worker 回收、EOS／NULL 或既有復原判定 |

**判讀標準**。基線先列各層間隔的 P95 與最大值。建議首輪以「穩定直連時，Capture 期間沒有新出現的連續 1 秒 RTP 畫格時間戳或解碼停滯，既有 WebRTC session 無故重建為 0 次」作為工程驗收目標；接收端採樣需細於 1 秒，記錄採樣間隔。若基線本身未達標，分開呈現基線與 Capture 的差異，不宣稱通過。每次正式接受的 Capture 都應能追到唯一 attempt；存證失敗、取消、舊世代結果誤上報必須為 0 次。

## 5. 交付與回退

以 1109 為基底，建議每一批各自提交。第一批先交付「慢 Capture 時預覽仍更新」的自動化證據；第二、三批完成後才判定完整檢驗流程是否達標。庫存樣本、SFIS／DMZ 契約、SN 長度、PATLITE 事件、HTTPS 與實際 MediaMTX 服務均按原版比對。若板上仍會閃，以第四批的量測結果決定下一個修改點。

板上比較保留兩個有版本標記的程式目錄與相同設定，分開測試資料。切換版本前正常停止相機與站點、確認持有者已退出。若工作未完成，先核對現有 DB、證據與 outbox 狀態；回退只切程式版本，保留當輪紀錄及 request ID，避免重複上報。PC 測試通過、開發板驗收、產線放行三項分別記錄。
